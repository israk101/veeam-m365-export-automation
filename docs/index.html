Operator + maintainer manual

Veeam M365
Restore Tester

A complete guide to deploying, operating and maintaining the Windows desktop application that verifies representative Veeam Backup for Microsoft 365 restores through local, non-destructive evidence extraction.

Version 1.2.4 Windows Python 3.12 + PySide6 PowerShell 7 + VB365
Deploy the application Understand the architecture
Purpose

What the application does

Veeam M365 Restore Tester turns a repeatable backup-restore verification script into an operator-friendly desktop workflow. It connects to the Veeam Backup for Microsoft 365 service installed on the same machine, discovers organizations and jobs, lets the operator queue one or many tests, and restores representative Exchange, OneDrive and SharePoint items to local storage.

A file is accepted as evidence only after it exists, is larger than zero bytes and can be hashed with SHA-256. The application then groups job outcomes by organization and writes an internal JSON record plus the selected client-facing documents.

Non-destructive

Samples are exported locally. Nothing is restored into Microsoft 365 and tenant content is not modified.

Evidence-oriented

Every accepted sample has file metadata and a SHA-256 hash, with structured job and workload outcomes.

Multi-job

Selected organization/job pairs are isolated and processed sequentially, then summarized per organization.

Interpret the result correctly This is a representative sampling test, not an exhaustive restore of every protected item. A successful result demonstrates that selected content could be opened and exported from the tested restore point under the conditions of that run.

Step-by-step

Deploy on a Veeam machine

  1. Obtain a trusted package.
    Clone/download the repository or receive the portable folder from your controlled build process. When using the tracked executable from Git, Git LFS must materialize the real binary rather than a pointer.
  2. Keep the portable folder intact.
    The recommended fast-start distributable consists of VeeamM365RestoreTester.exe and its adjacent _internal directory. ZIP and transfer the whole directory. The repository's compatibility one-file EXE is standalone but starts more slowly.
  3. Place it in a stable local directory.
    Do not run directly from inside a ZIP or a transient email/download preview. A locally extracted folder also avoids network-zone and performance issues.
  4. Verify integrity.
    Calculate SHA-256 and compare it with the release value from the repository or your organization's release record.
  5. Validate PowerShell and Veeam.
    Open PowerShell 7 and run the checks below before launching the GUI.
  6. Start the executable.
    Approve the UAC prompt. The application should show “PowerShell 7 ready” and “Administrator” in its shell status area.
  7. Confirm inventory.
    The Run test page should display organizations and their jobs. If it does not, use the troubleshooting entries for discovery/module/connection failures.
  8. Run a controlled acceptance test.
    Begin with one known test job and Don't run backup jobs enabled. Verify the JSON, an enabled client report and the evidence folder before expanding use.
# Runtime prerequisites
pwsh.exe --version
pwsh.exe -NoProfile -Command "Get-Module -ListAvailable Veeam.Archiver.PowerShell"

# Verify the packaged launcher

Operator workflow

Run the first restore verification

  1. Open Run test. Wait for the read-only organization/job inventory. Refresh only when Veeam configuration changed or discovery previously failed.
  2. Find and select jobs. Type any part of an organization or job name. Check individual jobs, a whole organization, or use Select visible.
  3. Review the selection summary. Search can hide checked rows, so confirm the total selected job/organization count before running.
  4. Choose the restore root. The default is C:\VeeamRestoreLocalTest. Use a local volume with suitable capacity and access controls.
  5. Choose backup behavior. Keep Don't run backup jobs checked for a faster test of existing restore points. Clear it only when you intend to execute every selected backup job first.
  6. Start the queue. The setup controls become read-only during execution. Watch current job, phase, elapsed time and live log.
  7. Review completion. Inspect overall status and each workload. Open the final organization directory and confirm requested report formats.
Backup mode changes real Veeam stateDiscovery and restore extraction are read-only relative to tenant data, but clearing Don't run backup jobs calls Start-VBOJob for each selected job.
Interface reference

What each page does

Dashboard

Shows the newest accepted final JSON report, aggregate outcome and representative Exchange/OneDrive/SharePoint details. It is a summary surface, not a test configuration page.

Run test

The primary operating page. It owns discovery, search, selection, restore root, backup behavior, queue controls, phase, timer and live output.

Reports

Scans final report folders, lists history by modification time, displays English outcomes and internal duration, and opens final folders or available TXT/HTML/PDF documents.

Settings

Stores operational defaults: restore root, per-organization retention, default use of existing restore points, report formats and an advanced custom script path.

Run test search behavior

  • Matching is case-insensitive and uses Unicode-aware casefold().
  • If the organization name matches, all jobs beneath it remain visible.
  • If only job names match, the parent organization plus matching jobs are visible.
  • Filtering does not reconnect to Veeam, rebuild the tree or change checks.
  • Select visible/Clear visible modify only visible job rows; hidden selections remain selected.
  • Clearing the query restores all inventory rows and preserved state.
Execution semantics

Multi-organization and multi-job tests

Checked rows are flattened into ordered PendingJob(org_name, job_name) records. The queue is serial: after one PowerShell child exits, its result is collected and the next child begins. The application never runs two selected Veeam restore tests concurrently.

Checked tree→PendingJob queue→One QProcess→Collect result→Next job→Group by org

Isolation rules

  • Each pair receives Batch_<timestamp>\Jobs\<safe-org>\<safe-job>.
  • Organization and job names are passed as separate process arguments.
  • A discovered report is accepted only when its job name matches and it was produced after that job started.
  • Completed records retain organization, job, exit code, report path, parsed report and measured seconds.
  • Final aggregation partitions completed records by organization before creating client output.

Why execution is sequential

Veeam backup jobs and Explorer restore sessions can consume significant local resources. Serial processing avoids session contention, prevents interleaved evidence, simplifies interruption and makes the live log attributable to exactly one queue item. The trade-off is elapsed time: a batch duration is approximately the sum of its job durations plus reporting overhead.

Stop behavior

Stop requires confirmation. Pending items are cleared, the active PowerShell process receives a terminate request, and the app waits up to 2.5 seconds before forcing a kill. Already generated temporary files may remain if a run is interrupted; they are not presented as a completed final report unless final aggregation succeeds.

Technical design

Architecture and process boundaries

The design separates user interaction, orchestration and Veeam-specific automation. Python never imports the Veeam module. PowerShell never owns the desktop interface or final cross-job history.

UI layer

app.py and ui/ render state and collect user intent. They do not call Veeam cmdlets directly.

Core layer

core/ owns process adapters, paths, configuration, aggregation, reports and retention.

Automation layer

scripts/ owns local Veeam discovery, backup and workload-specific extraction.

Responsiveness

Both discovery and job execution use Qt QProcess. Qt signals deliver output and completion back to the event loop; the main UI thread is not blocked waiting for PowerShell. The elapsed clock uses a monotonic source so system clock adjustments cannot make a run duration move backward or jump.

Resource resolution

core.paths.resource_path() selects the source repository root during development or PyInstaller's runtime resource root when packaged. Unless Settings specifies a trusted custom engine, the canonical embedded script is resolved from scripts/.

Inventory

Discovery, parsing and search

  1. InventoryDiscovery starts PowerShell 7 with no profile and the bundled inventory script.
  2. The script verifies/imports Veeam.Archiver.PowerShell, connects to localhost and enumerates sorted organizations.
  3. For each organization, it prefers Get-VBOJob -Organization and contains a compatibility fallback that filters the global job list by organization identity.
  4. It writes one compressed JSON payload prefixed with __VEEAM_INVENTORY__ and disconnects in finally.
  5. Python scans output from the end, parses only the marked line and requires an object containing an Organizations array.
  6. The tree loads current inventory and reapplies valid persisted checks.
__VEEAM_INVENTORY__{
  "Server": "localhost",
  "Organizations": [
    {
      "Name": "contoso.onmicrosoft.com",
      "Id": "...",
      "Jobs": [{ "Name": "M365 Backup", "Id": "..." }]
    }
  ]
}

Marker framing is important: Veeam or PowerShell may emit informational text around structured output. The parser does not mistake that text for inventory JSON.

One queued job

PowerShell backup and restore engine

The engine receives a single organization/job pair. It creates a timestamped run directory, imports the module, connects locally and verifies that the named organization and job exist before doing any backup or restore work.

Mode A: existing restore point

When the GUI passes -SkipBackup, the engine records SkippedByUser and proceeds directly to the latest available restore point lookup for the selected job. This mode is faster and avoids starting a production backup job.

Mode B: backup then restore

Without -SkipBackup, the engine calls Start-VBOJob, remembers the start time/session, polls until completion and validates the final backup status. Only then does it obtain a restore point and begin sample extraction.

Restore points stay job-boundThe lookup is Get-VBORestorePoint -Job $job -Latest. If the selected job has no restore point, that queue item fails clearly. The engine does not fall back to the newest restore point of the organization, because it could belong to another job.

Resilience

How a sample becomes valid evidence

Random selection alone is insufficient because Explorer APIs can return folder containers, stale items or objects that export to an empty result. RestoreSampleHelpers.ps1 uses an isolated, bounded verification pipeline.

  1. Filter. Reject null items, blank names and objects whose IsContainer or IsFolder property is true. OneDrive can additionally require a filename extension.
  2. Randomize. Shuffle eligible candidates so repeated tests do not always prove the same object.
  3. Bound. Attempt no more than MaxSampleAttempts candidates (default 25, accepted 1–1000).
  4. Isolate. Export one candidate into its own temporary attempt directory.
  5. Inspect. Recursively find regular files and keep only files larger than zero bytes.
  6. Copy safely. Copy the largest valid output into the workload evidence directory; add a short GUID suffix if a name already exists.
  7. Verify. Recheck final size and calculate SHA-256 from the final copy.
  8. Clean. Delete each attempt directory and the temporary workspace whether the attempt passed or failed.
Empty folders no longer decide the workload resultA folder-like candidate is rejected before export. If an object still exports no non-empty file, the helper logs a warning and tries another candidate until success, candidate exhaustion or the configured attempt limit.
Finalization

Aggregation and organization isolation

When the queue finishes, build_organization_summaries() preserves job order but partitions records by organization. Duration for an organization is the sum of its measured job durations. Each organization receives a separate final directory and report set.

For each workload, the summary prefers the first successful structured result from that organization's jobs. If there is no successful result, it retains the first available workload record so errors or not-configured information are not lost. Evidence copy then tries final representative paths and per-job report paths, taking only existing files.

Finalization order

  1. Create the safe organization and RestoreTest_* directory.
  2. Copy representative workload evidence and update final LocalFile paths.
  3. Write mandatory JSON.
  4. Write enabled TXT, HTML and PDF formats.
  5. Apply retention to that organization.
  6. After all organization JSON files exist, remove the temporary batch tree.
  7. Refresh Dashboard and Reports.
Interpretation

Status and exit-code model

Canonical statusInterpretationTypical operator action
SUCCESSValidated usable evidence exists and the evaluated result has no contradictory workload failure.Review/store evidence according to policy.
WARNINGSome usable evidence exists but the aggregate is partial, mixed or otherwise requires attention.Read per-job/workload details; rerun or investigate failed workload.
FAILEDNo acceptable successful evidence could be established or a hard process/job failure occurred.Use live log, per-job report and Troubleshooting.
NOT CONFIGUREDThe workload is absent or not protected for that job/restore point.Confirm this is expected in Veeam job scope.

Legacy labels such as SUCCESSO, FALLITO, ATTENZIONE and underscore variants are normalized before display. The application evaluates structured workload evidence as well as exit code, because a non-zero code can coexist with valid partial evidence. The JSON AllSuccessful boolean remains the strict success signal.

Filesystem

Storage lifecycle and retention

Temporary staging

<root>\Batch_YYYYMMDD_HHMMSS\
└── Jobs\
    └── <safe-organization>\
        └── <safe-job>\
            └── RestoreTest_...\per-job output

Final storage

<root>\<safe-organization>\RestoreTest_YYYYMMDD_HHMMSS\...

Names are sanitized to letters, numbers, dots, underscores and hyphens. Retention considers only direct child directories that exactly match RestoreTest_\d{8}_\d{6}. It sorts by timestamped name, clamps the minimum keep count to one, and deletes the oldest until the configured limit is satisfied.

Retention is deletionCompleted evidence older than the configured per-organization count is recursively removed and is not sent to the Recycle Bin. If evidence must be preserved for audit, archive it outside the managed restore root or set an appropriate limit before running new tests.

Verification

Test strategy and confidence boundaries

python -m pytest -q

The automated suite verifies deterministic behavior that can run without a live Veeam installation: settings, discovery parsing, tree filtering/check preservation, process arguments, status normalization, multi-organization grouping, evidence copying, report format selection, report history, duration, retention, PDF completion and staging cleanup.

What unit tests cannot proveThey do not prove that a particular Veeam server version, job, restore point, repository object model, permission set or Explorer installation will succeed. “31 passed” validates the application logic covered by those tests, not a production VB365 end-to-end run.

Protection

Security, privacy and safety

  • Least data movement: only representative items are extracted, but those items can still contain personal or confidential information.
  • Local destination: the engine exports to the configured Windows filesystem, not back into Microsoft 365.
  • No GUI credential store: Veeam connectivity/authentication remains in the installed local environment.
  • Elevated execution: the packaged process requests administrator privileges. Treat its binary, bundled scripts and custom script setting as privileged code.
  • Execution policy: the child uses -ExecutionPolicy Bypass for that invocation. Validate release hashes and source provenance rather than relying on local script policy as integrity verification.
  • Metadata exposure: JSON can include organization/job names, workload identity, local paths, hashes and errors. Client documents intentionally show a simpler model but still require appropriate handling.
  • Filesystem controls: restrict restore-root ACLs, avoid broad shares, encrypt storage where required and align retention with policy.
Custom script pathSettings can point the elevated runner to a different PowerShell file. Use this only for reviewed, trusted automation. Do not accept a script path supplied by an untrusted party.

Explicit boundaries

Known limits and design trade-offs

  • The application samples up to one accepted item per workload, not every item in the restore point.
  • It targets the local VB365 service (localhost); remote-server selection is not implemented.
  • Job execution is sequential by design, so large selections can take a long time.
  • PDF output depends on the large bundled Qt WebEngine/Chromium runtime.
  • Optional HTML/PDF exceptions are intentionally non-fatal after JSON; the operator must confirm required client artifacts.
  • Filesystem-based history has no external database, centralized concurrency or tamper-evident signing.
  • Retention permanently deletes matching old final directories rather than archiving them.
  • Compatibility with Veeam APIs is ultimately validated by live tests on the intended Veeam version and protected workload shapes.
